== A. Pipeline findings (code-level) ==
Path read: submitCloudPhoto -> reserve/begin/complete (VisitorService) -> jobs/spine-<spine-uuid>
(QUEUED, CLOUD_PRIVATE, generation) -> worker listTasks -> cleanupLocalTask -> cloudQueuedForWorker
-> photos.read(generation) + sha check -> dispatchLocalTask -> claim -> execute -> verify -> publish.
 1. 11 x WITHDRAWN with claimed=0 is correct behaviour (confirmed by code), not a bug.
 2. REAL BUG: any exception from photos.read (CLOUD_PHOTO_UNAVAILABLE on 15 s timeout/token,
    GENERATION_CHANGED, SIZE) or from dispatch propagated out of pollCloudSpineTasks, and the
    script's main() had no catch around the loop, so ONE bad/transient job (or a Firestore blip in
    listTasks) terminated the whole worker process. A QUEUED job could then sit with no worker.
    Fix: per-task isolation in pollCloudSpineTasks (reason-coded, pass continues); script loop
    survives a failed poll and logs {pollError: CODE}. Pre-claim errors are free to retry (nothing sent
    to a model); a claimed job is no longer QUEUED so it is never started twice.
 3. REAL GAP: `--workers=N` was parsed/validated but never used (single sequential loop, so one
    ~7 min job blocked every other queued person), and acquireLock() existed but was never called
    although the worker design says one process per scratch dir. Now N loops share one in-flight set
    (default 1 = unchanged) and the lock is taken (stale lock of a dead pid is taken over).
    BEHAVIOUR CHANGE: a second worker on the same scratch dir now exits WORKER_ALREADY_RUNNING.
 4. Order: loop started at a random offset. Now queued jobs first, oldest first (FIFO); concurrent
    loops still never collide (in-flight check+insert have no await between them).
 5. Listing read every CLOUD_PRIVATE doc in full (incl. consent/owner/digest) and then ran up to 3
    transactions per doc per 5 s poll, including long-finished WITHDRAWN ones. Now .select()s six
    non-sensitive fields and does not visit WITHDRAWN jobs whose cleanup is finished (counted as
    "settled"). Cleanup of anything not yet clean is unchanged (PUBLISHED/expired still visited).
 Not weakened: consent, digest check, generation pinning, session check, withdrawal cleanup, GCS
 policy, quality gate, UNKNOWN-never-resent. No automatic retry of any paid attempt was added.

   stuck marker). Warnings are information only; nothing is retried.

 preparedAt (markPrepared), finishedAt (publish / fail / review / unknown). Requeue sets
 queuedAt=now and clears startedAt/preparedAt/finishedAt (new attempt). Old records stay valid.
 !! DEPLOY ORDER: recordSchema is strict. A worker running OLD code cannot parse a record that has
 these fields, so it would silently never claim it (RECORD_INVALID with the new code). Update and
 restart the VM worker BEFORE (or together with) any web revision that writes them. Preview uses a
 separate namespace so it is unaffected; production is the risk. Not surfaced in admin UI yet.
